# Integration target: relationships and rules

**Status: proposed design, not deployed.** This reference combines the [current 9-table schema](database-schema.sql) with the [16-table additive proposal](integration-schema-proposal.sql). Download the [one-page integration ERD](opticapture-integration-erd-quick.svg) or [detailed integration ERD](opticapture-integration-erd-detailed.svg). The proposed SQL is executable for review on a fresh copy, but it is **not** a migration and must not be applied to a live database as-is.

The design follows [Initial Integration Plan.md](Initial%20Integration%20Plan.md): the existing platform owns official stores, users, catalog, and live inventory quantity. OptiCapture stores local mappings, inherited-SSO launch evidence, scan/count evidence, export artifacts, and reconciliation. The first application path is a reviewed Excel round trip; API application is later work.

## Entity inventory and ownership

| Area | Current tables | Proposed tables | Owner of authoritative value |
| --- | --- | --- | --- |
| Identity and store scope | `stores`, `users`, `user_stores` | `integration_sources`, `store_external_mappings`, `external_user_identities`, `sso_store_grants`, `sso_launch_receipts` | Existing platform for primary identity, role, and store scope; OptiCapture for local access mapping, per-store grant record, and replay record |
| Catalog intake | `categories`, `inventory` | `catalog_imports`, `catalog_import_rows` | Existing platform for official item identity and live quantity; OptiCapture for local working catalog and import history |
| Capture and count | `scan_sessions`, `session_items` | `session_devices`, `scan_events`, `count_commits`, `count_commit_lines`, `count_line_contributors` | OptiCapture for scanner identity, append-only scan history, and immutable committed count snapshot with per-scanner attribution |
| Export | — | `count_exports`, `count_export_lines` | OptiCapture for exact generated result artifact and rows |
| Reconciliation | — | `reconciliation_runs`, `reconciliation_lines` | External platform for applied quantity; OptiCapture for evidence of comparison |
| Operations | `logs`, `schema_migrations` | — | OptiCapture |

All current tables, columns, and seven enforced FKs remain as documented in [Current relationships and rules](DATABASE_RELATIONSHIPS_CURRENT.md). The proposal adds no columns to existing tables. It uses `inventory.external_system`, `external_store_id`, `external_category_id`, `external_item_id`, and `external_sku` already present, while adding dedicated external store and user identity mappings.

The proposal adds `idx_scan_sessions_id_store` on the existing session table so SQLite can enforce the proposed composite `(session_id, store_id)` FK. It adds no current-table columns or runtime behavior by itself. Two triggers make the new `scan_events` table append-only.

**Product direction (2026-10-01).** Scanning's primary purpose is adding new items to the catalog. Counting stock is deferred until that baseline works. The count-oriented tables below (`count_commits`, `count_commit_lines`, `count_line_contributors`, `count_exports`, `count_export_lines`, and reconciliation) are a later phase. The first integration phase needs only identity and SSO, catalog import, and capture of new items with attribution. The [new-item handoff design](NEW_ITEM_HANDOFF.md) proposes how those items are sent to the platform and linked back.

**Design decisions (2026-10-01).** These resolve two gaps found when the plan was checked against the code:

- **Per-scan attribution:** every scan, adjustment, and removal is an append-only `scan_events` row. `session_items` remains the mutable running total. Today a staged row loses its `device_id` as soon as a second phone scans the same UPC (`getMergedDeviceId` in `src/server/routes/sessions.ts`), so the plan's "counted by" export field could not be filled for shared sessions.
- **Scanner identity:** a phone's `device_id` is registered per session in `session_devices`. It is bound to a user either by the phone's authenticated app/SSO cookie or by an admin assigning the device. The OTP scan flow remains unchanged.
- **Superadmin store access:** an SSO launch, including one by an external superadmin, needs an explicit `sso_store_grants` row for that exact store and a provisioned `user_stores` membership. External superadmins receive the read-only `auditor` role per store, never local `users.role = 'superadmin'`. This follows the plan's rule that store access must never be inferred from role alone.
- **Timestamp format:** every stored timestamp is UTC text in the `datetime('now')` form, `YYYY-MM-DD HH:MM:SS`. Each proposed timestamp column has `CHECK (col IS datetime(col))`, which rejects ISO strings, fractional seconds, and unparseable values while still allowing `NULL` in nullable columns. Files sent to the external platform (count exports) use ISO 8601 UTC with `Z`, converted with `toIsoUtc()`. The current app follows the same rule since migration 18.

## Proposed foreign keys and cardinality

Each listed FK is parent one to child zero-to-many unless constrained further by a `UNIQUE` key. A nullable child column makes the parent optional for that child. All proposed FKs have `NO ACTION` delete/update behavior. The current seven FKs plus the 49 proposed FKs total **56** enforced relationships in the combined design.

| Child table | Enforced references | Nullability and purpose |
| --- | --- | --- |
| `store_external_mappings` | `source_id → integration_sources.id`; `store_id → stores.id` | Both required; one local/external store mapping per source |
| `external_user_identities` | `source_id → integration_sources.id`; `user_id → users.id` | Both required; one external user identity per source/local user |
| `sso_store_grants` | `source_id → integration_sources.id`; `user_id → users.id`; `store_id → stores.id`; (`source_id`, `store_id`) → `store_external_mappings`; (`source_id`, `user_id`) → `external_user_identities` | All required; one grant per source/user/store, so a mapped identity is explicitly granted each store it may enter |
| `sso_launch_receipts` | `source_id → integration_sources.id`; `user_id → users.id`; `store_id → stores.id`; (`source_id`, `user_id`, `store_id`) → `sso_store_grants`; (`user_id`, `store_id`) → `user_stores` | All required; a launch needs both a grant for that exact store and the provisioned membership before the token is marked consumed |
| `session_devices` | (`session_id`, `store_id`) → `scan_sessions`; `user_id → users.id`; `bound_by → users.id` | Session/store required; bound user optional until the device is bound; `bound_by` only for admin assignment |
| `scan_events` | (`session_id`, `store_id`) → `scan_sessions`; (`session_id`, `device_id`) → `session_devices`; `actor_user_id → users.id` | Session/store required; device must be registered in that session when present; actor optional only for scans from an unbound device |
| `catalog_imports` | `source_id → integration_sources.id`; `store_id → stores.id`; `imported_by → users.id`; (`source_id`, `store_id`) → `store_external_mappings` | Source/store and mapping required; actor optional |
| `catalog_import_rows` | `import_id → catalog_imports.id`; `inventory_id → inventory.id` | Import required; local inventory target optional for rejected rows |
| `count_commits` | (`session_id`, `store_id`) → `scan_sessions`; `store_id → stores.id`; `committed_by → users.id`; (`catalog_import_id`, `store_id`) → `catalog_imports` | Session/store/committer required; optional import baseline must be in the same store |
| `count_commit_lines` | `commit_id → count_commits.id`; `inventory_id → inventory.id`; `counted_by_user_id → users.id`; `external_system → integration_sources.id` | Commit required; item, scanner, and external source optional for unmapped lines |
| `count_line_contributors` | `count_line_id → count_commit_lines.id`; `actor_user_id → users.id` | Line required; actor optional only for `unattributed` rows, which must still name the device |
| `count_exports` | (`commit_id`, `store_id`) → `count_commits`; `source_id → integration_sources.id`; `store_id → stores.id`; `generated_by → users.id`; (`source_id`, `store_id`) → `store_external_mappings` | All required; commit, source mapping, and export agree on local store |
| `count_export_lines` | (`export_id`, `commit_id`) → `count_exports(id, commit_id)`; (`count_line_id`, `commit_id`) → `count_commit_lines(id, commit_id)` | Both composite FKs required; they enforce that exported rows come from the export's commit |
| `reconciliation_runs` | (`export_id`, `store_id`) → `count_exports`; `store_id → stores.id`; `reviewed_by → users.id` | Export/store required and aligned; reviewer optional |
| `reconciliation_lines` | `run_id → reconciliation_runs.id`; `count_line_id → count_commit_lines.id`; `export_line_id → count_export_lines.id` | Run/count line required; export line optional for unmapped/missing rows |

`count_commit_lines.source_session_item_id` and `scan_events.session_item_id` are deliberately **snapshot values, not FKs**: current staging rows can be deleted. History tables (`session_devices`, `scan_events`, `count_line_contributors`) reference `users`, not `user_stores`, so revoking a membership is never blocked by past scans; membership is checked by the service when a device is bound or an event is written. The four current app associations without FKs (`scan_sessions.user_id/store_id` and `logs.user_id/store_id`) remain unenforced in this additive proposal. Existing `inventory.external_system` and external IDs also remain plain text; the new `count_commit_lines.external_system` is FK-backed.

## Keys, identity, and idempotency

- `integration_sources.id` is the stable local code that should match the `inventory.external_system` value for mapped items. `(issuer, audience)` is unique. Signing keys and secrets are **not** stored in this draft schema.
- `store_external_mappings` uniquely maps `(source_id, external_store_id)` and `(source_id, store_id)`. A source cannot silently map one external store to two local stores or vice versa.
- `external_user_identities` uniquely maps `(source_id, external_user_id)` and `(source_id, user_id)`. Local `users` may have no password for inherited SSO, but the current `users.username` and store-scoped uniqueness still apply.
- `sso_store_grants` has composite PK `(source_id, user_id, store_id)`. Its composite FKs require a mapped source/store and a source/user identity. `granted_role` is limited to `owner`, `taker`, or `auditor`. `created_membership` records whether the grant created the `user_stores` row, so revocation removes only memberships that SSO created. `expires_at` is required; an expired or revoked grant must not authorize a launch or a request.
- `sso_launch_receipts` has composite PK `(source_id, token_id_hash)`. Its composite FKs require a grant for that exact source/user/store and a user/store membership before insertion. Insert after signature, issuer, audience, expiry, role, and store validation, in a transaction that rejects a repeated token ID. Store a digest, not the raw token or nonce. Purge only after the accepted replay window has closed.
- `catalog_imports` records source file URI/hash, source export time if known, counts, status, and optional idempotency key. Its unique `(source_id, store_id, idempotency_key)` prevents duplicate requests only when a non-null key is supplied; the file hash alone is not unique. `catalog_import_rows` is unique per `(import_id, row_number)` and retains rejected-row reasons.
- `session_devices` is keyed by `(session_id, device_id)`. `CHECK` constraints keep `binding`, `user_id`, `bound_at`, and `bound_by` consistent: an unbound device has no user, and only an `admin_assigned` binding names the admin.
- `scan_events` rows cannot be updated or deleted (triggers abort). A `scan` has a positive delta and a device or actor. An `adjust` (nonzero) or `remove` (zero or negative) always names the acting user. For each `(session_id, upc)`, the sum of `quantity_delta` must equal the staged `session_items.quantity`; the service maintains this in the same transaction as the staging write.
- `count_commits.session_id` is unique: the proposed integrated count workflow creates one immutable count snapshot per scan session. `last_scan_event_id` records the last event included in it. `count_commit_lines` has unique line numbers and source staged IDs per commit; multiple `NULL` source staged IDs remain allowed by SQLite.
- `count_line_contributors` is unique per line, actor, and device (an expression index treats `NULL` actor/device as values). An `unattributed` row must name its device.
- `count_exports` permits deliberate re-exports via `attempt_number`, unique for `(commit_id, source_id, attempt_number)`. The export ID, artifact hash, and exact `count_export_lines` are the idempotency/review references for the external platform. Each export line occurs once per export and points to one commit line.
- These keys prevent duplicate local export attempts; they cannot prevent the external platform from applying the same file twice. The external import process must deduplicate by export/batch ID or perform an equivalent reviewed check.
- A `count_exports` row exists only after an artifact is generated; `delivery_failed` means the existing artifact could not be delivered. Failures before artifact creation require a separate operational log or attempt record if that detail is needed.
- `reconciliation_runs` can recur for an export as more external outcomes arrive. `reconciliation_lines` is unique per `(run_id, count_line_id)`. No `applied externally` claim is made merely because a file was generated or delivered.

## Required workflow rules

### 1. SSO launch and store scope

The external platform authenticates the user. OptiCapture validates the signed token's signature, issuer, audience, issued/expiry times, unique ID, role/permissions, external store ID, and mapped local store. It resolves the external user through `external_user_identities`. It then creates or refreshes the `sso_store_grants` row for the token's store and maps the external role to `granted_role`. Next it creates or updates the matching `user_stores` membership and uses the same active-store enforcement as existing requests. Grant, identity, and membership must all exist before the replay receipt is inserted, in one transaction.

Each launch names one store, so an external superadmin builds up access one grant at a time. They receive `auditor` in each launched store. SSO-provisioned users must never get local `users.role = 'superadmin'`: the auth middleware gives that role cross-store access without memberships, which would bypass the grants. The role string `superadmin` must not be used for `user_stores.role` either, because `requireOwner` accepts it as owner. `auditor` fails `requireOwner` and `requireOwnerOrTaker`, so it is read-only by default. The app must explicitly allow it on the read routes the plan gives superadmins (inventory status, logs, integration history). Request middleware must also reject memberships whose grant has expired or been revoked. On revocation, delete the `user_stores` row only when `created_membership = 1`. The draft SQL checks that `expires_at > issued_at`. That text comparison is reliable because every proposed timestamp column only accepts the canonical UTC form, so convert the token's `iat`/`exp` with `toSqliteUtc()` before inserting. The endpoint and key rotation policy are not yet implemented.

### 2. Catalog import and external identity

Map a real external export's stable item ID to `inventory.external_item_id`; use UPC only for scanning. Require a nonempty `external_system` for imported IDs because the current partial unique index can still allow duplicates when that component is `NULL`. Validate that the incoming external store maps to the selected local store and that any category belongs to that store. Stage and validate rows before changing inventory; write `catalog_imports` and `catalog_import_rows` with accepted/rejected totals and reasons. The SQL constrains nonnegative counts but does not enforce `row_count = accepted_count + rejected_count`; the importer must do so when completing a batch. Keep the source artifact and hash for retry/audit.

### 3. Scan capture and scanner identity

When a phone opens the QR link, register its `device_id` in `session_devices`. If the request carries a valid app/SSO cookie for a member of the session's store, bind it as `authenticated`. Otherwise leave it `unbound` and let an admin assign it to a store member from the desktop session view (`admin_assigned`). Each scan writes one `scan_events` row in the same transaction as the `session_items` upsert. Its `actor_user_id` is the device's bound user at that moment. Binding a device later does not rewrite earlier events. Desktop quantity edits write `adjust` events with the editor as actor. Item deletion and "clear items" write `remove` events. A UPC change on a staged row is a `remove` of the old UPC plus an `adjust` on the new one. Because events cannot be deleted, `DELETE /session/:id` must become a cancel (status change) once a session has events; today it hard-deletes uncommitted sessions.

### 4. Commit a count snapshot

Review a scan session, freeze its selected `session_items`, and atomically write `count_commits` plus `count_commit_lines` **before** deleting or changing staging rows. Snapshot item identity, local previous quantity, counted quantity, and timestamps. Record the event high-water mark in `last_scan_event_id`. Verify that each line's event total equals its counted quantity, then aggregate events into `count_line_contributors` per actor and device. Attribute an unbound device's events through its binding at commit time (`device_binding`), or leave them `unattributed`. Set `count_commit_lines.counted_by_user_id` (and `device_id`) only when the line has exactly one contributor; otherwise export "counted by" from the contributor rows. `first_scanned_at` and `last_scanned_at` come from the events. `delta_quantity` is generated as counted minus previous. A `mapped` line requires nonempty external system and external item ID; an `unmapped` line remains visible for review. The SQL permits a blank `source_session_item_id` for synthetic adjustments, but the application must record why it exists. The existing commit endpoint adds new items and marks existing items as seen. It does not record counts, so this snapshot flow would be a separate step. Capture, not counting, is now the product's primary purpose, so this count-oriented section is due to be reshaped around new-item capture and shelf verification. Commit records and their lines are design-intended to be immutable; the draft DDL does not yet add immutability triggers or database privileges.

### 5. Export and reconciliation

Generate a reviewed count-result artifact from mapped snapshot lines. `count_export_lines` record the exact external item ID and quantities serialized into that attempt; the file URI and SHA-256 hash preserve the artifact identity. Composite FKs enforce the export's commit/store and source/store mapping. Service code must still verify that each line's external source and item ID match the export target and the selected store's inventory mapping. Never push directly into official quantity in phase 1; transfer the file through the external platform's reviewed import. Record the external batch/receipt and compare each applied quantity with the exported count in `reconciliation_lines`. Preserve unmapped, rejected, missing, and mismatched rows with reasons. Only mark a reconciliation run `matched` after independent external confirmation, not after download or submission.

### 6. Deletion, retention, and tenant boundaries

All planned tables default to `NO ACTION`; delete policies must be decided explicitly. Keep committed count, export, reconciliation, and scan-event evidence longer than the current 90-day `logs` retention. Purging `scan_events` requires a deliberate retention migration that lifts the append-only triggers. Retain SSO replay digests only as long as security policy requires. While a receipt exists, it blocks deleting the matching `user_stores` row, so purge expired receipts before removing a revoked membership. Keep grant rows as access history. Composite FKs now enforce the store match between a commit and its session/import, an export and its commit/source mapping, and a reconciliation run and its export. Service code must still check that optional `inventory_id` rows and categories belong to the same store, that a baseline import and count lines use the intended export source, and that each reconciliation line belongs to the run's export and commit. Existing `scan_sessions` and `logs` store/user IDs remain unenforced.

## Contracts to confirm before migration

The local design is internally valid, but the following facts cannot be inferred from the current repository or integration plan. They must be fixed against the real external platform before implementing migrations and endpoints:

1. Actual Excel column names, ID formats, UPC uniqueness policy, units, quantity meaning (absolute count versus adjustment), and accepted result format.
2. External store/category/item identifiers and whether one OptiCapture store can map to multiple external locations. The current proposal assumes one external store ID per source/local store.
3. SSO issuer/audience, signing algorithm/key discovery, exact claims and permission mapping, expiration and logout/refresh behavior.
4. External apply receipt format, batch ID/idempotency behavior, whether line-level accepted/rejected quantities are available, and reconciliation timing.
5. Artifact storage, retention, access control, allowed re-export/revision policy, whether the external platform accepts ISO 8601 UTC with `Z` or needs another date/time representation in import files, and whether count quantities can be fractional. The draft uses nonnegative integer quantities, matching the current `inventory.quantity` declaration.

**Validation status:** The combined proposal creates 25 tables with 56 FK relationships in an in-memory SQLite database and passes `PRAGMA foreign_key_check`. This validates its SQL structure, **not** the unknown external contract or implementation behavior.
